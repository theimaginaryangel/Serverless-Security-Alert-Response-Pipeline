**Author:** Benny Duah

## 1. Executive Summary

Security operations teams face significant operational friction due to alert volume generated by automated compliance scanning and threat detection services (e.g., AWS Security Hub, Amazon GuardDuty). Manual triage introduces latency that directly increases the blast radius of compromised credentials and exposed storage resources.

The Serverless Security Alert Response Pipeline (SSARP) is an automated, event-driven containment system. It ingests findings, enriches alerts with context, triages severity, executes automated containment protocols (IAM DenyAll isolation) with strict administrative guardrails, persists audit trails, and provides a real-time operational dashboard for security personnel and auditors.

## 3. Engineering & Design Patterns

### 3.1 Separation of Duties (Hybrid IaC Architecture)
To comply with enterprise security auditing standards, the infrastructure is segregated into distinct layers:
1. **Tier 1 — Security Foundation (`security-base.yaml`):** Declared in native CloudFormation YAML. Houses sensitive IAM roles and notification topics. Isolating these resources allows security auditors to review privilege boundaries without parsing application codebase.
2. **Tier 2 — Application Core (`lib/ssarp-stack.ts`):** Declared in AWS CDK v2 (TypeScript). Utilizes `CfnInclude` to ingest Tier 1 templates and programmatically provisions Step Functions, EventBridge rules, SQS dead-letter queues, DynamoDB tables, and Lambda functions.
3. **Tier 3 — Continuous Delivery (`lib/pipeline-stack.ts`):** Implements AWS CodePipeline via `aws-cdk-lib/pipelines`. Uses an AWS CodeStar Connection to automate builds (`npm ci && npm run build && npx cdk synth`) and cloud deployments on every Git push.

### 3.2 Automated Containment & Security Guardrails
The quarantine worker (`lambdas/quarantine.py`) enforces strict isolation logic:
- **Administrative Allowlist:** Hardcoded protection against self-lockout for sensitive roles (`Admin`, `AdministratorAccess`, `cli-user`).
- **Inline Policy Attachment:** Attaches an explicit `DenyAll` policy (`AutomatedQuarantine-DenyAll`) using `boto3.client('iam')`.
- **Fault-Tolerant Execution:** Catches `NoSuchEntity` exceptions gracefully for simulated or ephemeral targets while ensuring full audit persistence.

### 3.3 Dynamic Configuration (AWS Systems Manager Parameter Store)
To eliminate hardcoded values and configuration drift:
- The CDK deployment publishes resource identifiers directly to SSM:
  - `/ssarp/production/audit-table-name`
  - `/ssarp/production/state-machine-arn`
- The Next.js API routes discover runtime infrastructure dynamically using the AWS SSM SDK.

## 4. Component Specification

| Component | Technology | Role |
| :--- | :--- | :--- |
| **Ingestion Engine** | Amazon EventBridge | Catches `aws.securityhub` findings and routes to the SQS Buffer Queue. |
| **Buffer Queue & Routing** | Amazon SQS & Lambda | SQS absorbs high-throughput spikes; Dispatcher Lambda reads messages and triggers the state machine. |
| **Workflow Engine** | AWS Step Functions | Orchestrates the multi-stage triage DAG (Standard Workflow). |
| **Triage Workers** | AWS Lambda (Python 3.12) | Executes lightweight enrichment, severity analysis, and IAM quarantine logic (30s timeout). |
| **Audit Repository** | Amazon DynamoDB | Key-value storage (`alertId` primary key) with pay-per-request billing. |
| **Notification Bus** | Amazon SNS | Broadcasts compliance and alert notifications to subscribers. |
| **Frontend Portal** | Next.js 16 (App Router), Tailwind CSS | Real-time monitoring UI with interactive attack simulation controls. |

## 5. Verification & Testing

The system supports automated validation through an integrated Red Team simulation engine:
1. **Simulation Dispatch:** The Next.js API (`/api/simulate`) invokes `StartExecutionCommand` on Step Functions and emits to EventBridge.
2. **Workflow Progression:** Step Functions validates JSON schemas, enriches resource targets, evaluates risk levels, applies quarantine logic, and records state.
3. **Audit Verification:** DynamoDB scan queries reflect live status (`ISOLATED`, `LOGGED`, `SKIPPED`).
## 6. Engineering Challenges & Problem Resolution
 
| # | Challenge Encountered | Root Cause | Engineering Solution |
| :--- | :--- | :--- | :--- |
| **1** | **Lambda Cold-Start Execution Timeout** | Default Lambda timeout (3.0s) was insufficient during initial SDK initialization across IAM and DynamoDB. | Elevated timeout parameter to `30s` in CDK constructor (`timeout: cdk.Duration.seconds(30)`). |
| **2** | **Potential Administrative Lockout** | Unconstrained quarantine automation risked isolating administrative or CI/CD deployment roles. | Integrated an immutable allowlist (`PROTECTED_ROLES`) in `quarantine.py` to enforce safety guardrails. |
| **3** | **Dynamic Resource Discovery** | Generated resource names (DynamoDB table, Step Functions ARN) create coupling issues if hardcoded in `.env`. | Leveraged AWS Systems Manager (SSM) Parameter Store for runtime service discovery via SDK. |
| **4** | **Local SDK Execution Latency** | Node.js AWS SDK hung for ~60s per request attempting to reach EC2 metadata (`169.254.169.254`) on Windows. | Enforced `AWS_EC2_METADATA_DISABLED="true"` in local environment configuration. |
| **5** | **Safe Demonstration for Evaluators** | Demonstrating incident response without generating real vulnerabilities or corrupting audit metrics. | Engineered an interactive simulation engine (`/api/simulate`) and scoped sandbox purge route (`/api/reset`). |
